## 1. Ürün tanımı ve ana sınırlar — KİLİTLİ

BellekPad, **Web-First, AI-First, Local-First** bir çalışma ortamıdır. Tarayıcıdaki kendi UI'ından yerel model çalıştırma, kalıcı çoklu sohbet, görsel üretim, workflow, proje/not yönetimi yapılacaktır. Web arayüzü bir **yerel backend** ile haberleşir; yalnızca tarayıcıyla doğrudan GPU veya keyfî disklere erişim varsayılmaz. Electron/masaüstü paketlemesi ve mobil istemci ilk teslimi belirleyen zorunluluk değildir; sonradan ele alınabilir.

Referans yerleşim: **ChatGPT / LM Studio** (sol navigasyon, geniş içerik, alt kompozisyon alanı, bağlamsal sağ panel), **Forge** (kolay üretim formu), **ComfyUI** (grafik/workflow). Referanslar UI davranışıdır, başka ürünlerin ekranını kopyalama talimatı değildir. Sağ Inspector ihtiyaca göre açılır. Sohbet bir modal değil, birinci sınıf çalışma yüzeyidir.

İlk ana çalışma yüzeyleri: **Chat, Image Studio, Workflow Studio, Models, Projects/Notes**. Ayrıntılı Word/Illustrator tipi **Artboard/Layout Editor** ayrı inceleme merceğine **ERTELENDİ**; ortak metin çekirdeğiyle ileride birlikte çalışabilmesi korunur.

## 3. Metin sohbeti / çoklu model — KİLİTLİ

Üç konuşma politikası **kilitli ürün yeteneği** olarak kaydedildi:

1. **Parallel:** Aynı kullanıcı mesajına bağımsız çoklu model yanıtları; modeller birbirlerinin yanıtını zorunlu olarak görmez.
2. **Roundtable:** Seçilmiş modeller sıralı konuşur, uygun kapsamda birbirlerinin yanıtını görür.
3. **Orchestrated:** Konuşma yöneticisi, görev/konuşmacı seçimi ve konuşmanın bitişini idare eder. Yöneticinin mutlaka ayrı LLM olması gerekmez.

**KİLİTLİ kontrol özellikleri:** Kullanıcı tarafından başlatma/durdurma, tur sınırı, konuşma dalları/yanıt alternatifleri, model bazlı katılımcı rolü, konuşma kaydı, tek veya çoklu model çağrısı. Kullanıcı dışındaki modellerin birbirleriyle konuşması **mümkün olmalı**, fakat döngü sınırsız değil. **Çoklu konuşma = eşzamanlı GPU yüklemesi zorunluluğu değil**; sıra/parallel yürütme politikası ayrıca uygulanabilir.

**AÇIK:** R3 veri şeması, mesaj/branch yapısı, geçmişin modele aktarım şekli, streaming protokolü, orkestrasyon stratejisi, tool-calling ve model-adapter yetenekleri.

## 4. Model kütüphanesi ve çalıştırma — KİLİTLİ beklentiler

- BellekPad kendi UI'ından modelleri yükleyip çalıştırabilmeli; **LM Studio veya Comfy arayüzünü ayrıca açma zorunluluğu olmayacak**. Harici çalışan motor bağlantısı isteğe bağlı olabilir.
- Modeller kullanıcı tarafından seçilen **farklı disk/dizinlerde** barınır; gereksiz kopyalanmaz veya merkezi BellekPad model klasörüne taşınmaz. Yalnız kullanıcının kaydettiği dizinlerde tarama yapılır.
- **GGUF ve Safetensors birincil dosya biçimleri**; gerektiğinde tokenizer, JSON manifest, VAE, text encoder, mmproj gibi ilişkili varlıklar desteklenir. Dosya uzantısı tek başına model mimarisini belirlemez.
- Uygulama özel bir **Model Registry / Component Registry** ile model kimliği, yol, aile, component ilişkileri ve seçili runtime profilini tutar.
- **Python + venv/uv**, PyTorch + Transformers, `llama.cpp` / Python binding, ComfyUI / Diffusers gibi çalışma yolları teknik araştırmaya açıktır; henüz tek motor **kilitlenmedi**.
- BellekPad kendi süreçlerinin başlatma/durdurma/iptal/hata durumlarını yönetir. Runtime bağımlılıkları mümkünse **izole edilmiş ortamlarda** sürümlendirilir.

### Donanım sorumluluğu ayrımı — KİLİTLİ

**Modelin boyutu/quantization/VRAM/RAM'e sığıp sığmayacağı kullanıcının tercihidir.** Mühendislik planı kullanıcıyı tekrar tekrar model ağırlığı konusunda eğitmeye, keyfî model boyutu limiti koymaya veya seçimlerini engellemeye dönüşmeyecek. Uygulamanın teknik sorumluluğu: kullanıcı seçimini yürütmek, gerçek backend hatasını açıkça göstermek, isteğe bağlı kaynak bilgisini sunmak, süreçleri temiz sonlandırmak ve veri kaybetmemek. Kapasite tahmini varsa opsiyonel bilgi niteliğinde kalır; ürün kapsamının merkezine konulmaz.

## 5. Görsel üretim / workflow — KİLİTLİ davranışlar

- Bir görsel üretim işi için **bir ana model**; ihtiyaç duyduğunda harici veya paket içi CLIP / text encoder(lar) / VAE ile birleşir.
- Modeller tek bir sabit yükleme düzenine zorlanmaz: SD 1.5, SDXL, FLUX, Qwen Image, Z-Image ve başka ailelerin bileşen topolojileri manifest/loader'a göre farklıdır.
- **LoRA Stack:** Çoklu LoRA, ayrı ağırlıklar, gerektiğinde model/CLIP etkisini ayrı kontrol etme.
- Workflow, **preset** olarak önceden kaydedilebilir; model, encoder, VAE, LoRA, sampler/scheduler gibi alanlar hazır olabilir.
- Kullanıcı çalıştırmadan önce prompt, conditioning, steps, CFG/guidance, sampler/scheduler, seed, denoise, resolution/scale, reference image gibi parametreleri UI'dan değiştirebilir. Bunlar model/workflow şemasına bağlıdır; her parametrenin her modelde geçerli olduğu varsayılmaz.
- Sohbetten görsel üretim istendiğinde doğal dildeki parametreler **yapılandırılmış generation request** hâline getirilir, workflow destekleri doğrulanır ve yürütülür. Destek dışı bir parametre sessizce yutulmaz.
- **Generate UI** (Forge benzeri kolay panel) ve **Workflow UI** (Comfy benzeri React Flow grafiği) birbirinden ayrıdır; kullanıcı basit üretim yapmak için node şemasıyla uğraşmak zorunda değildir.
- Workflow tasarımı yapmak, her seferinde workflow'u yeniden kurmak anlamına gelmez.

### Henüz çözülmemiş teknoloji kararları — AÇIK

1. **Inference / graph engine:** Yönetilen ComfyUI backend'i, Diffusers tabanlı BellekPad yürütücüsü veya hibrit strateji.
2. **GPU compute:** CUDA bir arayüz veya Comfy'nin alternatifi değil; PyTorch/engine altında kullanılan hesaplama katmanıdır. Desteklenen backend, sürüm ve paketleme stratejisi araştırılacak.
3. **Runtime Supervisor:** Python süreç yöneticisi mi, farklı worker'lar mı; iş kuyruğu, iptal, izolasyon, process lifecycle, dependency setup ve güncelleme/geri dönüş.
4. **Comfy uyumluluğu:** Workflow JSON içe/dışa aktarma, custom node desteği, çalıştırma sonuçları, sürüm farkları.
5. **İş motoru ile UI ayrımı:** **BellekPad'in kendi React UI'ı kilitli**; Comfy veya başka motor kullanımı, onların arayüzünü zorunlu kılmaz.

**Kritik ayrım:** **ComfyUI** workflow/yürütme altyapısı, **CUDA** GPU hesaplama platformu, **React + React Flow** ise kullanıcı arayüzüdür. Bunlar birbirinin yerine geçen seçenekler değildir.

## 6. Veri ve bağlam — KİLİTLİ niyetler

- Sohbet geçmişi ve kullanıcı projeleri **kullanıcının seçtiği ve kolayca yedekleyebildiği bir klasörde** saklanır. Kullanıcı verileri geçici veya belirsiz Roaming/Temp gömülerine hapsedilmez.

- Uygulama, kullanıcı modelinin üzerine zorunlu genel ahlaki/NSFW moderasyon katmanı eklemeyi ürün özelliği olarak hedeflemez; modelin kendi davranışı ile uygulamanın dosya/süreç güvenliği ayrı konulardır.

## 10. CORE → API → UI bütünlük protokolü — KİLİTLİ (28.10.2026)

**Kullanıcı direktifi:** Backend mantığı ve prosedürleri önceliklidir; frontend bu sözleşmeyi doğru temsil eder, onunla çelişen eylemler üretmez. Bir modül; çekirdek, servis, API, kalıcılık ve UI arasında yarım bırakılmadan, uçtan uca çalışır hâlde teslim edilir. Önce plan, sonra onaylı uygulama. Görsel şıklık temel işlev ve veri doğruluğunun yerine geçmez.

### 10.1 Mühendislik ilkeleri

1. **Core-first, contract-first:** Her özellik önce amaç, girdiler/çıktılar, veri yapısı, geçerli durumlar, işlemler, hata davranışı ve sistem sınırlarıyla tanımlanır. Sonra kodlanır.
2. **Backend tek yetkili yürütücüdür:** İş kuralları, kaynak ve görev durumları, izinler, dosya erişimi, kalıcılık ve geçiş doğrulaması backend'de sağlanır; frontend kontrollerine güvenilmez.
3. **Frontend sözleşmenin arayüzüdür:** Backend'in gerçekten sağladığı yetenekler ve güncel durum neyse UI yalnız bunları sunar. Ön yüz, backend'in kabul etmeyeceği aksiyonları meşru işlem gibi göstermez; arayüz estetiği sistem mantığını delmez.
4. **Uçtan uca özellik dilimi:** Bir modülün `core → service/supervisor → API/events → data/persistence → frontend → integration/E2E` hattı tek sözleşmeye dayanır. API'de var ama UI'da yok; UI'da var ama backend'de yok türü yarım özellikler tamamlanmış sayılmaz.
5. **Durum makineleri ve deterministik akış:** Idle/starting/ready/busy/stopping/error gibi durumlar gerçek süreç olaylarından üretilir; geçersiz geçişler kontrol edilir. İptal, zaman aşımı, tekrar istek, eşzamanlılık, süreç çökmesi ve yeniden başlatma davranışı önceden tanımlanır.
6. **Hata yalıtımı ve gözlemlenebilirlik:** Hatalı UI isteği backend'i çökertecek şekilde etkileyemez; API doğrulaması, işlemsel tutarlılık, görev kimliği, güvenli hata kodları ve ölçülebilir olay kayıtları bulunur. Kullanıcı verisi ve yerel dosya yolları gereksiz yere sızdırılmaz.
7. **UX rafine, mantık değişmez:** Kullanıcıya uygun sade ekranlar tasarlanır ancak teknik ayrıntılar gerektiğinde erişilebilir kalır. Her küçük backend adımına ayrı bir UI icat edilmez. UI son kullanıcıya anlamlı bir iş akışını bütün halinde sunar.
8. **Kayıpsız ve kanıtlı teslim:** Verinin sessiz kaybı, sahte başarı durumu, backend yerine arayüzde uydurulmuş özellik, doğrulanmamış 'tamamlandı' ifadesi kabul edilmez. Sıfır hata mutlak olarak garanti edilemez; hedef, açık sözleşmeler ve gerçek kabul testleriyle hata riskini sistematik olarak azaltmaktır.

### 10.2 Her modül için zorunlu tasarım dosyası

| Gerekli bölüm | Açıklama |
|---|---|
| İş sözleşmesi | Neden var, kullanıcı eylemi, girdiler/çıktılar ve sınırlamalar |
| Çekirdek algoritma | Modül sorumlulukları, invariant'lar, ön/son koşullar |
| Durum ve hata modeli | State transitions, hata kodları, timeout/cancel/retry, concurrency |
| API/olay sözleşmesi | Tipli request/response, streaming/event yapısı, sürümlendirme |
| Veri sözleşmesi | Storage şeması, atomiklik, migration, recovery |
| UI eşlemesi | Backend state → görünür durum; izinli komut → etkin kontrol |
| Test/kabul matrisi | Unit, contract, integration, gerçek runtime, E2E, failure-path |
| Bakım/değişim | Loglama, izolasyon, rollback, bağımlılık etki analizi |

### 10.3 Örnek: model yükleme modülü

- `UNLOADED → LOADING → READY → GENERATING → READY → UNLOADING → UNLOADED`; istisnalarda tanımlanmış `ERROR` geçişleri. Gerçek süreç davranışına göre durum kümesi modül tasarımında netleşir.
- UI'daki **Yükle**, **Üret**, **İptal**, **Boşalt** kontrolleri bu durum makinesine göre etkinleşir. Backend her isteği ayrıca doğrular; UI'dan atlanan/tekrarlanan komutlar süreci bozmaz.
- Yükleme başarısızsa UI 'hazır' göstermez. İşlem iptal edilirse backend işlemin ve kaynakların son durumunu belirler; UI yalnız olayı yansıtır.
- Bu yaklaşım zorunlu VRAM kapasite limiti oluşturma gerekçesi değildir. Kullanıcının model seçimi özgürlüğü korunur; sistem hataları dürüstçe yönetilir.

### 10.4 Uygulama teslim kapısı

**Plan → Kullanıcı onayı → Core uygulama → Contract test → Service/API → Persistence → UI mapping → Integration/E2E → Failure-path test → Kabul raporu.** İnce tasarım/son rötuşlar, sağlam ve uçtan uca çalışan davranıştan sonra gelir. Bir katmanda eksik kalan özellik, modül tamamlandı diye etiketlenmez. Bu mühendislik standardı R0–R7'nin tamamında bağlayıcıdır.

- **Editör seçimi: Tiptap + ProseMirror (KİLİTLİ teknoloji seçimi).** Görsel tasarım tamamen BellekPad'a aittir. Tek belge/notes editörü motoru; standart sohbet yanıtları streaming esnasında ayrı bir **okuma render'ı** olabilir. Tiptap'ın Markdown beta eklentisi, EFSS için kanonik serializer olarak kullanılmayacak. EFSS AST + özel Node/Mark adaptörleri + opaque/unsupported içeriği koruma; acceptance gate import→edit→export→reopen, Unicode/IME, table, custom vars, unknown extension üzerinde kayıpsızlık.
- **Workflow UI: React Flow (KİLİTLİ).** React Flow grafik geometri ve etkileşimlerini yönetir; backend'in kabul ettiği workflow tiplerini, bağlantı sınırlamalarını ve çalıştırılabilirliği kanonik olarak belirlemez. `node registry → graph schema → validation → engine-adapter → execution job → result/artifact` hattı tasarlanacak.
- **Görsel hesaplama başlangıç yönü: BellekPad yönetimindeki ayrı ComfyUI backend süreci.** Comfy'nin web arayüzünü çalıştırmak zorunlu değildir; BellekPad kendi React arayüzünü kullanır. Mevcut Comfy kurulumunu bağlama opsiyonel. Alternatif Diffusers worker'ı ilk uygulamanın ön koşulu değil, adapter genişletme imkânıdır. ComfyUI sürüm/özel node/API uyumluluğu ve kapalı kaynak dağıtımda lisans etkisi ayrıca çözülmelidir.
- **AI runtime yönü:** Python + FastAPI uygulama/supervisor çekirdeği; izole worker/env; GGUF için ayrı llama.cpp worker, safetensors/multimodal için desteklenen Transformers/PyTorch worker. Python `venv`, inference motorunun yerini tutmaz. İkinci motor, ilk motorun GUI'sine bağlı değildir. Somut runtime artifact/pinning ve bağlama ayrıntıları teknik tasarım konusu.
- **Frontend/back-end sözleşmesi (KİLİTLİ):** Core-first; typed schema, işlem/durum/hata modeli, persistence ve API/event sözleşmesi olmadan UI'da özellik vaat edilmez. Bir modül core→API→UI→E2E tamamlanmadan teslim sayılmaz.
- **Donanım tercihi:** Kullanıcı model boyutunu/kapasitesini kendisi belirler. Keyfî VRAM kilidi yoktur; başlatma hata ve kaynak durumu dürüst gösterilir.

### Karar bekleyen değil, tasarlanması gereken teknik işler

1. **EFSS ↔ Tiptap tam şema ve round-trip ispatı.** Özellikle `&variable`, bilinmeyen uzantılar, iç içe tablolar, source-preservation ve başlatma/yeniden açma.
2. **Comfy adapter ve sürümlü API sözleşmesi.** `object_info` bazlı node yetenekleri; grafik→API workflow dönüşümü; job kuyruğu; iptal/progress ve artifact alma; custom node uyumluluğu.
3. **Supervisor / worker süreci.** Başlatma, readiness, crash isolation, restart/cancel, sürüm ve izole Python ortamı yönetimi; kanonik backend durum makinesi.
4. **Local web güvenlik ve veri sözleşmesi.** `127.0.0.1`, oturum/yerel yetkilendirme, kullanıcının seçtiği data root, SQLite dosya stratejisi, snapshot-backup ve migration.
5. **ComfyUI dağıtım lisansı, tedarik zinciri ve motor pinning.** GPL-3.0 yükümlülükleri için dağıtım öncesi inceleme; motor sürümü/custom node uyumluluk matrisi.
6. **UI tasarım sistemi** (tipografi, erişilebilirlik, paneller, inspector davranışı), ana algoritma ve API onayından sonra nihai görsel uygulama.

**Mevcut aşama:** PLAN/R0 kararların kapanması → yeni şubenin açılması (yalnız repo eylemi) → detaylı modül sözleşmeleri. ### Çözülen dört mimari karar

1. **Runtime Supervisor:** Python/FastAPI tarafından yönetilen worker yaşam döngüsü; renderer süreç komutu veya model yolu çalıştıramaz. `stopped/starting/ready/stopping/failed` durumları, süreç denetimi, gerçek readiness, port çakışması koruması, başlatılırken durdurma. Comfy kurulumu ve Windows üzerinde gerçek inference sonraki kabul kapısıdır.
2. **EFSS–Tiptap:** EFSS metni kalıcı kaynaktır; güvenle desteklenmeyen bilinmeyen/karmaşık bloklar opaque/read-only tutulur. İlk gerçek API + Tiptap Notes kesitinde basit satırlar kaynak revizyon ve blok hash sözleşmesiyle düzenlenir. Genel zengin metin, tablolar, değişkenler, çok satır henüz desteklenmiyor; kaynak sessizce kaybolmuyor.
3. **React Flow–Comfy:** UI grafiği backend'de Comfy `/object_info` ile doğrulanıp `/prompt` biçimine derlenir. Node tipi, girişler, bağlantı türleri, döngü ve eksik girdiler denetlenir. İş kimliği /history ve hedefli iptal adaptörü mevcuttur. Gerçek model ve görsel çıktı testi yapılmadı.
4. **Kalıcılık/güvenlik/dağıtım:** Kullanıcı tarafından seçilen `BELLEKPAD_DATA_ROOT`, SQLite WAL, revizyon denetimi ve SQLite online backup. Yerel 127.0.0.1 API ve Host/Origin kontrolü. Eski proprietary LICENSE aynen korundu; ComfyUI GPL çekirdeği depoya kopyalanmadı. Dağıtım lisansı, paketleme, web oturum auth, dosya/asset yedek bütünlüğü henüz release kapılarıdır.
